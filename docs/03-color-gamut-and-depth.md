# 03 色域、色深与色彩

[01](01-hdr-and-sdr.md) 说 HDR 多出来的三样东西里，第三样是色域。这一篇把它拆成三个**互相独立**的轴：

* **色域**（gamut）：能表示多鲜艳的颜色——由原色坐标决定。
* **色深**（bit depth）：能表示多少级——由每通道位数决定。
* **传递函数**（transfer）：码值怎么映射到光——[02](02-pq-and-brightness.md) 已讲。

三者可以任意组合：8bit sRGB 是"窄色域 + 浅色深"，10bit BT.2020 PQ 是"宽色域 + 深色深 + 绝对亮度"。把色域和色深混为一谈，是"我的图是 10bit 所以颜色更鲜艳"这类说法的来源——并不是。

## 1. 颜色从哪来：光谱、三刺激值、同色异谱

物理上，光是一段光谱功率分布（SPD）。人眼视网膜有三种视锥（L/M/S，峰值约 564/534/420 nm），把 SPD 积分成三个响应值，大脑再解释成颜色[\[1\]](#r1)。

关键结论：**无穷多种 SPD 可以产生同一组三刺激值**，这叫同色异谱（metamerism）[\[2\]](#r2)。所以：

* 用三个数（R/G/B）就能"骗过"眼睛复现大部分颜色——这是三原色显示的基础。
* 但"看起来一样"不等于"光谱一样"：同色异谱对观察者、光源、视角都敏感。两个颜色在一种光下匹配，换个光源可能就不匹配。
* 相机/扫描仪/显示器的"颜色"都是三刺激值层面的近似，不是光谱层面的还原。

这也解释了为什么"色域"是一个**二维色度平面上的三角形**：固定亮度、固定白点后，三个原色的色度坐标确定一个三角形，三角形内的颜色可以用非负的 R/G/B 混合得到。

## 2. CIE 1931 与色域三角形

CIE 1931 xy 色度图把三刺激值归一化投影到二维平面（x+y+z=1）。图上的马蹄形是所有可见色，但它是**色度**图，不含亮度信息；同一个 (x,y) 在不同亮度下是不同颜色。

一个色域由三个原色坐标 + 白点定义[\[6\]](#r6)：

| 色域               | R (x,y)        | G (x,y)        | B (x,y)        | 白点                   | 用途        |
| ---------------- | -------------- | -------------- | -------------- | -------------------- | --------- |
| sRGB / BT.709    | (0.640, 0.330) | (0.300, 0.600) | (0.150, 0.060) | D65 (0.3127, 0.3290) | 网络、SDR 视频 |
| DCI-P3（影院）       | (0.680, 0.320) | (0.265, 0.690) | (0.150, 0.060) | DCI 白 (0.314, 0.351) | 数字电影      |
| Display P3       | 同上             | 同上             | 同上             | D65                  | Apple 设备  |
| Adobe RGB (1998) | (0.640, 0.330) | (0.210, 0.710) | (0.150, 0.060) | D65                  | 印刷/摄影     |
| BT.2020          | (0.708, 0.292) | (0.170, 0.797) | (0.131, 0.046) | D65                  | UHDTV、HDR |

覆盖率的常见口径是"占 CIE 1931 可见色度面积的比例"：

| 色域            | 覆盖率（CIE 1931 xy） |
| ------------- | ---------------- |
| BT.709 / sRGB | 约 35.9%          |
| Adobe RGB     | 约 52.1%          |
| DCI-P3        | 约 53.6%          |
| BT.2020       | 约 75.8%          |

数据来自 Wikipedia Rec.2020 条目[\[3\]](#r3)，与 Christie 等厂商文档的数字一致。注意这是**色度面积**，不是"能显示的颜色数量"；而且 BT.2020 的原色是单色光附近的点，实际显示器几乎做不到 100% 覆盖，消费级面板通常报 90–95% 的 BT.2020 覆盖率（按面积或按体积口径不同，数字会差很多）。

### 2.1 覆盖率口径的坑

* **xy 面积覆盖率** vs **u'v' 面积覆盖率**：后者更接近感知均匀，同一块屏的两个数字能差 10 个百分点以上。
* **2D 色域面积** vs **3D 色域体积**：后者还考虑亮度，HDR 显示器常报"体积"。
* **"覆盖 BT.2020 的 95%"** 可能是面积、可能是体积、可能是某个特定亮度切片。比较前先问口径。

本项目不测量显示器，只做**色彩空间转换**：把 sRGB 的线性光转到 BT.2020 的线性光，然后按 BT.2020 原色编码。源图本来就没有 BT.2020 以外的颜色，转换不会"增加"颜色，只是换一套坐标表示。

## 3. 从 BT.709 到 BT.2020：矩阵怎么来

两个色域共享 D65 白点，所以转换是一个 3×3 线性矩阵[\[6\]](#r6)。推导分三步：

1. 由原色坐标 + 白点，算出每个色域的 `RGB → XYZ` 矩阵（每列是原色在 XYZ 中的位置，再按白点归一化）。
2. 求逆得到 `XYZ → RGB`。
3. 组合：`RGB_2020 = M_2020⁻¹ · M_709 · RGB_709`。

数值结果（保留 6 位）：

```text
[ R2020 ]   [ 0.627404  0.329283  0.043313 ]   [ R709 ]
[ G2020 ] = [ 0.069097  0.919540  0.011362 ] · [ G709 ]
[ B2020 ]   [ 0.016391  0.088013  0.895595 ]   [ B709 ]
```

`hdrgainmap/color.py` 里的 `BT709_TO_2020` 就是这个矩阵（四位小数版本），`to_bt2020()` 做 `rgb @ M.T`。

几个性质：

* **每行和为 1**：白点不变，`(1,1,1)` 映射到 `(1,1,1)`。
* **非对角项为正**：BT.2020 比 BT.709 宽，709 的纯色在 2020 里是"不那么纯"的混合，所以需要正的串色项。
* **反向转换会出现负值**：BT.2020 的纯绿在 BT.709 里表示不出来，逆矩阵会把某些分量算成负数。负值不能直接 clip——clip 会改变色相。正确做法是色域映射（gamut mapping）：降饱和度直到落入目标三角形，尽量保持色相和亮度。

这也说明"把 BT.2020 图转成 sRGB"不是无损的：超出 709 的颜色必须被压回来。

### 3.1 为什么必须先线性化

矩阵乘法只对**线性光**成立。sRGB 码值是经过 gamma 编码的，直接对码值做矩阵乘法，等于在一条弯曲的坐标上做线性变换，结果会偏色——暗部偏得尤其厉害。正确顺序：

```text
sRGB 码值 → sRGB EOTF → 线性光 → 3×3 矩阵 → BT.2020 线性光 → PQ 编码
```

本项目 `_hdr_band()` 正是这个顺序：`srgb_to_linear(rgb) * exp2(expo)` → `to_bt2020(lin)` → `pq_oetf(lin * 203)`。`expo` 是逐通道的（见 [04](04-gain-map.md) 第 7 节）。

### 3.2 亮度系数

在线性 RGB 里算亮度（luma）要用对应色域的系数：

```text
BT.709:  Y = 0.2126 R + 0.7152 G + 0.0722 B
BT.2020: Y = 0.2627 R + 0.6780 G + 0.0593 B
```

本项目所有"亮度场"分析都在 sRGB/BT.709 线性光里做（`luma()` 用 709 系数），最后才转 2020。这是合理的：源图按 sRGB 解释，分析也应该在源的坐标系里做；转换只发生在输出编码前。

## 4. 色深：多少级才够

色深是每通道的量化位数：

| 位深 | 每通道级数    | 典型用途                                  |
| -- | -------- | ------------------------------------- |
| 8  | 256      | SDR 分发、JPEG/PNG、网页                    |
| 10 | 1024     | HDR10、HEVC Main10、手机 HDR              |
| 12 | 4096     | Dolby Vision 母版、AVIF/HEIC 高质量、HDR 中间片 |
| 16 | 65536    | PNG 16bit、PFM、中间运算                    |
| 24 | 16777216 | JPEG XL 的高位深模式（项目用它存 PQ）              |

位深决定"台阶"有多粗。判断标准不是绝对级数，而是**相邻级值的相对差**是否低于人眼阈值（约 1–2%）：

* 8bit sRGB 在亮部（0.5–1.0）每级约 0.4–1%，够用；在暗部（线性 0.001）每级相对差可达 20% 以上，所以暗部渐变容易 banding。
* 8bit **线性** 更糟：暗部只有几个级值。这就是为什么必须 gamma/PQ 编码后再量化。
* 10bit PQ 在中高亮约 0.9–1%，刚好压线；深暗部（0.01 nit）仍有 9% 的台阶（见 [02](02-pq-and-brightness.md) 第 4 节）。
* 12bit PQ 约 0.2–0.5%，感知无损。

### 4.1 色深和色域是两件事

* 8bit 也能表示 BT.2020 的颜色，只是每个原色方向只有 256 级，渐变会粗。
* 10bit sRGB 不会变鲜艳，只是渐变更细。
* "10bit 色彩"这个营销词通常指"10bit 面板 + 广色域 + HDR"，是三件事打包，不是单一指标。

### 4.2 抖动（dither）

量化误差是确定性的，会在渐变区形成规则条纹（banding）。抖动在量化前加一点噪声，把"规则条纹"打散成"随机噪点"，视觉上更舒服。

常见类型[\[7\]](#r7)：

* **有序抖动**（Bayer 矩阵）：规则图案，低成本，但可能看出网格。
* **误差扩散**（Floyd–Steinberg）：把量化误差传给邻居，质量好，但难并行。
* **噪声抖动**：加均匀/三角/高斯噪声。三角分布（两个均匀分布之差）在相同方差下感知效果较好，且不会引入偏置。

本项目的增益图是 8bit RGB，量化前用了三角分布抖动：

```python
dither = rng_a.random(shape) - rng_b.random(shape)   # 范围 (-1, 1)，三角分布
gm_px = clip(code * 255 + dither, 0, 254)
```

即 ±1 个码值、标准差约 0.41 个码值。它必须加在**量化的最后一步**：半分辨率路径里，抖动若放在缩放前会被 LANCZOS 平均掉；现在全分辨率没有缩放，抖动直接加在取整前。

## 5. 色度采样

视频编码常把色度（Cb/Cr）降采样，因为人眼对色度细节不如亮度敏感[\[8\]](#r8)：

| 记号    | 含义      | 每 4 个亮度像素的色度样本 |
| ----- | ------- | -------------- |
| 4:4:4 | 不降采样    | 4              |
| 4:2:2 | 水平减半    | 2              |
| 4:2:0 | 水平垂直都减半 | 1              |

"4:2:0"里的数字不是比例，是 J:a:b 记号（a = 第一行色度样本数，b = 第二行）。4:2:0 的数据量是 4:4:4 的 50%（8bit）或接近 50%。

本项目的取舍：**所有格式都用 4:4:4**。理由是插画里大量饱和色块、文字描边、细线，4:2:0 会在边缘产生彩色溢出；质量优先的场景不值得为体积牺牲这个。代价是 AVIF 4:4:4 的体积约为 4:2:0 的三倍（实测 70.2MP 图：AVIF 71.4MB vs 常见 4:2:0 编码的二十多 MB），HEIC 同理。

HEIC 用 4:2:0 是个已知短板：pillow-heif 的编码路径只给 4:2:0，项目没有绕过。所以 HEIC 在这套产物里是"体积小、兼容好、但色度细节最弱"的一档。

## 6. 色彩管理：文件怎么告诉查看器"我是什么颜色"

一个 RGB 文件必须带三样信息，否则查看器只能猜：

1. **原色 + 白点**（primaries）
2. **传递函数**（transfer）
3. **矩阵/范围**（matrix coefficients、full range）

表达方式有三套，互相有优先级：

| 方式          | 在哪                                 | 表达力         |
| ----------- | ---------------------------------- | ----------- |
| ICC profile | JPEG APP2、PNG iCCP、HEIF colr（prof） | 最强，可带任意 LUT |
| CICP / nclx | PNG cICP、HEIF/AVIF colr（nclx）      | 整数枚举，标准组合   |
| sRGB 标记     | PNG sRGB chunk                     | 只说"我是 sRGB" |

HEIF/AVIF 的 `colr` box 有两种：`nclx`（枚举）和 `prof`（ICC）。`nclx` 里就是 CICP 的四个字段[\[5\]](#r5)：

| 字段                        | 值            | 含义                           |
| ------------------------- | ------------ | ---------------------------- |
| colour\_primaries         | 1 / 9        | BT.709 / BT.2020             |
| transfer\_characteristics | 13 / 16 / 18 | sRGB / PQ / HLG（本项目只写 16）    |
| matrix\_coefficients      | 0 / 9        | identity（RGB）/ BT.2020 非恒定亮度 |
| full\_range\_flag         | 1            | 全范围 0–255（或 0–1023 等）        |

PNG 第三版新增了 `cICP` chunk，并给出色彩块的优先级：**cICP > iCCP > sRGB > cHRM+gAMA**（规范 §4.3 "Color Chunk Priority"）[\[4\]](#r4)。也就是说，如果一张 PNG 同时有 cICP 和 iCCP，查看器应该听 cICP 的。本项目的 PNG 只写 cICP（9/16/0/1），不写 ICC，避免优先级打架。

### 6.1 本项目的色彩链路

```text
源文件
  ├─ EXIF Orientation → 转正
  ├─ alpha → 合成到黑/白底
  ├─ ICC → ImageCms 转到 sRGB（rendering intent = 0，感知）
  └─ 得到 float32 sRGB 码值（0–1）
        ↓
  luma() → 光场分析（BT.709 系数）
        ↓
  srgb_to_linear() × exp2(expo) → to_bt2020() → PQ → 16bit
        ↓
  写入容器 + cICP/nclx 标记
```

两个容易忽略的点：

* **ICC 转换用感知意图**（intent 0）。相对比色（intent 1）会保持白点但可能裁掉超色域颜色；感知意图会整体压缩，视觉上更平滑。对插画这种大面积平色，感知意图通常更稳。
* **转换后不再信任源 ICC**。输出容器写的是"BT.2020 + PQ"，不是源图的 profile；如果输出时还带着源 ICC，查看器可能按 ICC 解释 BT.2020 码值，直接偏色。所以 Ultra HDR 主图重写 ICC 为 sRGB，PNG/HEIC/AVIF 只写 CICP/nclx。

## 7. 常见错误清单

1. **在 gamma 码值上做矩阵/增益/混合。** 必须在线性光做。
2. **把"10bit"当"广色域"。** 两者独立。
3. **以为转 BT.2020 会让颜色变鲜艳。** 源图没有的颜色不会凭空出现；转换只改表示。
4. **BT.2020 → BT.709 直接 clip 负值。** 会改色相，应该做 gamut mapping。
5. **同时写 cICP 和 iCCP 且不一致。** 查看器按优先级选一个，另一个是隐患。
6. **HEIC/AVIF 写 matrix=6（BT.601）。** 解码器会按 601 转 RGB，画面偏色；BT.2020 应写 9。
7. **在 4:2:0 上期待锐利彩色边缘。** 色度已经减半，边缘溢出是格式决定的。
8. **抖动加在缩放之前。** 缩放会把噪声平均掉，等于没加；现在全分辨率输出，抖动直接进量化。
