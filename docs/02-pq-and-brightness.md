# 02 PQ 与亮度

[01](01-hdr-and-sdr.md) 说了 HDR 有两条路线：PQ 绝对、HLG 相对。本篇把 PQ 拆开：它为什么长这样、数字怎么算、203 nits 落在哪里、位深为什么必须是 10bit 起、以及"PQ 图在 SDR 屏上发灰"到底是哪一步错了。

一句话版本：**PQ 是一条把 0–10000 cd/m² 的绝对亮度压进 0–1 信号的曲线，按人眼对比敏感度分配码值；SDR 参考白 203 nits 在 PQ 里是 58%，不是 75%。**

## 1. 为什么需要传递函数

如果直接把线性光写进 8bit，会浪费绝大部分码值：线性 0–1 里，人眼能分辨的暗部只占最前面几个码值，而 0.5–1.0 这一段占了 128 个码值却几乎看不出差别。传递函数的作用就是**重新分配码值**，让"一个码值台阶"约等于"一个最小可辨差异"。

SDR 用的是幂函数（gamma 约 2.2–2.4），HDR 用的 PQ 则更彻底：它直接对**绝对亮度**做感知编码，目标是在 0.0001–10000 cd/m² 的整个范围里，相邻码值的亮度比大致恒定。这也是为什么 PQ 的公式里有四个常数、看起来不像人写的——它是从 Barten 的对比敏感度模型拟合出来的。

## 2. PQ 的数学

SMPTE ST 2084 定义[\[1\]](#r1)，ITU-R BT.2100 收为 HDR 传递函数之一[\[2\]](#r2)。记绝对亮度 `L`（cd/m²），归一化 `Y = L / 10000`，编码信号 `N ∈ [0,1]`。

**OETF（线性光 → 信号）**：

```text
N = ( (c1 + c2·Y^m1) / (1 + c3·Y^m1) )^m2
```

**EOTF（信号 → 线性光）**：

```text
p = N^(1/m2)
L = 10000 · ( max(p − c1, 0) / (c2 − c3·p) )^(1/m1)
```

常数（都是有理数，避免浮点误差）[\[4\]](#r4)：

| 常数 | 分数              | 十进制             |
| -- | --------------- | --------------- |
| m1 | 2610/16384      | 0.1593017578125 |
| m2 | 2523/4096 × 128 | 78.84375        |
| c1 | 3424/4096       | 0.8359375       |
| c2 | 2413/4096 × 32  | 18.8515625      |
| c3 | 2392/4096 × 32  | 18.6875         |

代码里对应 `hdrgainmap/color.py` 的 `PQ_M1`/`PQ_M2`/`PQ_C1`/`PQ_C2`/`PQ_C3`，以及 `pq_oetf(nits)` 与 `pq_eotf(code)`。

两个边界值得记住：

* `N = 0` → `L = 0`；`N = 1` → `L = 10000`（严格说是 10000 的极限，实际显示器到不了）。
* EOTF 里 `max(p − c1, 0)` 是必要的：`p < c1` 时物理上对应负亮度，直接算会得到复数/NaN。

### 2.1 为什么曲线长这样（直觉）

* **暗部**：`Y^m1` 在 `Y` 很小时变化剧烈，`N` 对 `L` 近似对数响应，所以 0.001–1 nit 这一大段被拉开，占了可观的码值。
* **亮部**：`Y → 1` 时 `c2·Y^m1` 主导，`N` 趋于 1，曲线变平，高光被压缩。
* **中段**：`c1/c2/c3` 让曲线在 100 nits 附近有一个近似"拐点"，兼顾暗部精度和亮部范围。

这不是"物理规律"，是**工程拟合**：目标函数是人眼在标准观看条件下的可辨差异，而不是线性或对数。

几个常被引用的锚点：

* **100 nits（SDR 参考白）→ 0.508**，正好在 PQ 的中点附近。
* **203 nits（HDR 参考白）→ 0.5807**，即 58%[\[5\]](#r5)。
* **1000 nits → 0.7518**，即 75%。
* **10000 nits → 1.0**。

注意 0.75 这个数：**HLG 的 75% 信号对应 203 nits，PQ 的 75% 信号对应 1000 nits。** 两条曲线在同一个"75%"上差了约 2.3 个 stop。这是 HDR 制作里最常见的张冠李戴（见第 7 节）。

## 4. 感知均匀性：台阶有多粗

光看码值不够，要看"相邻码值差多少亮度"。对 10bit PQ，取每个码值对应的亮度区间，相对步长如下：

|       亮度 | 10bit 相对步长 | 12bit 相对步长 |
| -------: | ---------: | ---------: |
| 0.01 nit |       9.1% |       2.3% |
|  0.1 nit |       3.7% |      0.93% |
|    1 nit |       1.9% |      0.48% |
|   10 nit |       1.2% |      0.31% |
|  100 nit |      0.97% |      0.24% |
|  203 nit |      0.94% |      0.23% |
| 1000 nit |      0.90% |      0.22% |

这组数字说明三件事：

1. **10bit PQ 在中高亮区刚好够用**：约 1% 的台阶，接近 Weber 阈值（人眼在背景亮度附近能分辨约 1–2% 的差异）。所以 10bit 是"能看"，不是"富余"。
2. **10bit 在深暗部不够**：0.01 nit 附近一个台阶就是 9%，暗部渐变会断层。这也是为什么 HDR 母版普遍 12bit，以及为什么"暗部 banding"是 HDR 的常见投诉。
3. **12bit 把台阶压到 0.2–0.5%**，远低于阈值，属于"感知无损"；16bit 更多是给中间运算和增益图元数据留余量，不是给人眼看的。

顺带解释 8bit PQ：到 203 nits 只用了 148 个码值，0–1 nit 只有 38 个码值。用它存 HDR，暗部必然 banding。**8bit + PQ 不是"不能存"，是"存了不好看"。**

## 5. 203 nits 为什么是 58%

[01](01-hdr-and-sdr.md) 从 HLG 推过一遍：75% HLG 信号 → 逆 OETF 得场景线性 0.265 → OOTF `1000 × 0.265^1.2 ≈ 202.5`。反过来，把 203 nits 代进 PQ：

```text
Y = 203 / 10000 = 0.0203
N = ((0.8359375 + 18.8515625·0.0203^0.1593) / (1 + 18.6875·0.0203^0.1593))^78.84375
  ≈ 0.5807
```

也就是 **58.07%**。行业文档里常直接写"203 nits ≈ 58% PQ"，例如 Light Illusion 的 HDR 解释页[\[3\]](#r3)。

为什么容易记混？因为两条曲线都叫"75% 白"，但参考系不同：

|                    | HLG                              | PQ         |
| ------------------ | -------------------------------- | ---------- |
| 参考对象               | 场景光                              | 显示光（绝对）    |
| 参考白 203 nits 的信号位置 | **75%**                          | **58%**    |
| 信号 75% 对应的亮度       | 203 nits（1000 nit 屏）[\[6\]](#r6) | 1000 nits  |
| 信号 100% 对应的亮度      | 显示器峰值（如 1000）                    | 10000 nits |

所以：

* 做 HLG：参考白写 75% 信号。
* 做 PQ：参考白写 58% 信号，峰值按内容需要写（常见 1000–4000 nits 对应 0.752–0.903）。
* 把 HLG 的 75% 直接当 PQ 码值用 → 参考白变 1000 nits，整张图过曝约 2.3 stop。
* 把 PQ 的 58% 当 HLG 75% 用 → 参考白变约 100 nits，整张图偏暗。

## 6. 峰值、元数据与显示端映射

PQ 只是"怎么编码"，不规定"这张图最高到多少"。内容峰值由创作决定，通过元数据告诉显示端[\[7\]](#r7)[\[8\]](#r8)：

| 元数据                                     | 含义                                           | 标准                    |
| --------------------------------------- | -------------------------------------------- | --------------------- |
| Mastering display primaries / luminance | 母版监视器的原色与最大/最小亮度                             | SMPTE ST 2086         |
| MaxCLL                                  | 全片单帧最大内容亮度（Maximum Content Light Level）      | CTA-861.3             |
| MaxFALL                                 | 全片帧平均最大亮度（Maximum Frame-Average Light Level） | CTA-861.3             |
| 动态元数据（逐帧/逐场景）                           | 每一帧的峰值与平均亮度                                  | HDR10+ / Dolby Vision |

显示端拿到这些信息后做 **tone mapping**：显示器峰值 600 nits，内容峰值 1000 nits，就得把 1000 压到 600，同时尽量保持相对关系。这一步发生在显示设备/播放器，不在文件里。所以：

* 同一个 PQ 文件，在 600 nit 和 1600 nit 的屏幕上"看起来"不完全一样，这是设计使然。
* 文件里写"峰值 1000 nits"不等于"每个像素都 1000 nits"；大多数像素仍在 0–203 之间，只有高光接近峰值。
* 没有元数据时，显示端只能猜（常见默认按 1000 nits 处理），结果可能偏暗或偏亮。

**PQ 直传 SDR 为什么会发灰？** SDR 显示器不知道这是 PQ，按 sRGB/BT.1886 解释码值。203 nits 的 PQ 码值 0.5807，被当成 sRGB 0.5807 显示，约等于 30 nits（`((0.5807+0.055)/1.055)^2.4 ≈ 0.297`，在 100 nit 屏上约 30 nits）。参考白从 203 掉到 30，画面又暗又平，暗部细节也糊在一起——这就是"发灰"的实感。反过来，把 SDR 图硬标成 PQ，1.0 会被解释成 10000 nits，直接过曝。

## 7. 本项目怎么用 PQ

`hdrgainmap/pipeline.py` 的 `_hdr_band()`（逐通道）：

```python
lin = srgb_to_linear(rgb) * exp2(expo)            # 线性光，1.0 = SDR 白，逐通道
hdr2020 = to_bt2020(lin)                          # BT.709 → BT.2020
code = pq_oetf(hdr2020 * 203.0)                   # SDR 白 = 203 nits
```

三步：线性化、转色域、乘 203 后编码。`peak = lin.max() * 203` 统计实际峰值（写进 `stats.peak_nits`）。

因为输出是 16bit（PNG/HEIC/AVIF），`_hdr_code()` 把 0–1 的 PQ 信号乘 65535 再四舍五入，按 2048 行分块处理以控制内存。16bit 的 PQ 在 203 nits 处有约 38055 个码值，远超感知需求，所以**本项目输出的 banding 风险主要来自源图 8bit 和增益图 8bit，不来自 HDR 编码本身**。

### 7.1 为什么不再输出 HLG

如果按 HLG 输出，`code = hlg_oetf(hdr2020, 1000/203)` 等价于把 `e = linear × 0.203` 直接套 OETF，得到参考白信号 **0.697**；而按 BT.2100 的 OOTF 反解，要让显示亮度落在 203 nits，场景线性应是 `(203/1000)^(1/1.2) ≈ 0.265`、信号 **0.750**。两者相差约 **0.48 stop**，SDR 白会被放在约 146 nits 的等效位置。

与其留一条"近似但和标准对不上"的分支，现在统一为 PQ：所有格式的参考白、峰值、元数据只有一种解释，文档也不用再教用户"HLG 输出为什么偏暗"。HLG 本身仍是有效标准，区别与用法留在 [01](01-hdr-and-sdr.md) 第 3.2 节作对照。

## 8. 常见错误清单

1. **把 PQ 码值当线性光运算。** 增益、混合、模糊都必须在线性光做；PQ 是编码，不是光。
2. **把 SDR 图直接打 PQ 标签。** 标签和码值必须一起转；只改标签 = 把 1.0 解释成 10000 nits。
3. **把 203 nits 当 75%。** PQ 里是 58%；75% 是 HLG 的说法。
4. **用 8bit 存 PQ。** 暗部只有几十个台阶，必然 banding。
5. **忽略 `max(p−c1,0)`。** 低码值会算出 NaN/复数。
6. **把"内容峰值"当"显示器峰值"。** 文件里的 1000 nits 是创作意图，显示端会按自己的能力 tone map。
7. **以为 PQ 图在 SDR 屏上"只是暗一点"。** 实际是参考白从 203 掉到约 30 nits，对比度和暗部层次一起塌。
