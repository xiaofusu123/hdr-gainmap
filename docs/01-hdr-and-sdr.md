# 01 HDR 与 SDR：定义和标准

先给结论：**SDR 和 HDR 不是"暗"和"亮"的区别，而是两套"信号值 ↔ 显示亮度"的约定。** 一套约定把 1.0 当作"显示器白"，另一套把 1.0 当作 10000 cd/m² 的绝对光。谁把这件事搞混，后面所有颜色、位深、增益图的问题都会跟着错。

本篇讲四件事：动态范围到底在量什么、SDR 的约定是什么、HDR 的两套约定（PQ/HLG）是什么、以及这些约定对应哪些标准文件。PQ 的数学细节放到 [02](02-pq-and-brightness.md)，色域和位深放到 [03](03-color-gamut-and-depth.md)。

## 1. "动态范围"的三个所指

同一个词在三种语境里指三个不同的东西，混用是绝大多数 HDR 讨论跑偏的起点。

| 说法        | 量的对象                    | 典型值                                                  | 谁关心        |
| --------- | ----------------------- | ---------------------------------------------------- | ---------- |
| 场景动态范围    | 真实场景里最亮和最暗**反射/发射**的光之比 | 晴天室外可达 10^4–10^5:1（约 13–17 stops）                    | 摄影、电影拍摄    |
| 显示动态范围    | 一块屏幕能同时输出的最亮与最暗之比       | SDR 显示器约 100–500:1 同时对比；HDR 电视标称 10^5:1 以上（含分区背光）    | 显示硬件、调色    |
| 编码/格式动态范围 | 一种文件格式能**表示**的亮度范围      | 8bit SDR 约 5–8 stops；PQ 编码 0–10000 cd/m²（约 20 stops） | 编解码、容器、本文档 |

PNG 第三版标准把后两者写进了术语表：SDR 是"能存储相对低动态范围（5–8 stops）的图像格式"，HDR 是"能存储接近或超过人眼瞬时动态范围（约 12–14 stops）的格式"[\[8\]](#r8)。注意它定义的是**格式能力**，不是"这张图看起来亮不亮"。

"stop"是光圈/曝光里的说法，一个 stop 就是亮度乘 2，所以 N 个 stop 的动态范围等于 2^N:1。换算成数量级：10 stops ≈ 1000:1，14 stops ≈ 16384:1，20 stops ≈ 10^6:1。

**本项目只处理第三件事的输入端**：一张已经存在、已经被压成 8bit SDR 的图片，把它重新包装成能表达更多高光的容器。场景动态范围在拍摄/绘制那一刻就丢失了，文件里没有"原本的 HDR 信息"可恢复——这一点决定了增益图只能"估"，不能"还原"（见 [04](04-gain-map.md)）。

### 1.1 亮度的单位

* **辐射亮度** `L`：单位 W/(sr·m²)，纯物理量，与人眼无关。
* **亮度** `Y`：单位 cd/m²，也叫 nit，是辐射亮度按人眼光谱灵敏度加权后的结果。日常说"这块屏 1000 nits"指的是它。
* **照度** `E`：单位 lx（= lm/m²），描述"落在表面上的光"，不是"表面发出来的光"。

严格说，屏幕像素发的是辐射亮度，文件里存的是编码值，中间隔着传递函数和显示器的 EOTF。日常把 nit 当"亮度"用没问题，但在推公式时要清楚自己在哪一层。

## 2. SDR 的约定

SDR（Standard Dynamic Range）不是"没有标准"，恰恰相反，它是一整套 tightly coupled 的约定：

| 维度   | SDR 的约定                                    | 标准                                |
| ---- | ------------------------------------------ | --------------------------------- |
| 原色   | BT.709 三原色（与 sRGB 相同）                      | ITU-R BT.709[\[2\]](#r2)          |
| 白点   | D65（x=0.3127, y=0.3290）                    | BT.709                            |
| 传递函数 | 显示端 BT.1886（约 gamma 2.4）；网页/文件常用 sRGB 分段曲线 | BT.1886[\[1\]](#r1)、IEC 61966-2-1 |
| 参考白  | **100 cd/m²**（BT.1886 的 L\_W）              | BT.1886                           |
| 黑位   | 理想为 0；实际受面板限制                              | —                                 |
| 位深   | 8bit/通道（消费级分发）                             | —                                 |
| 信号范围 | 全范围 0–255 或视频有限范围 16–235                   | —                                 |

关键在**参考白 100 cd/m²**：BT.1886 定义的 EOTF 把信号 1.0 映到 `L_W = 100 cd/m²`[\[1\]](#r1)。也就是说 SDR 是**显示参考**（display-referred）的：同一个文件，在 100 nit 校准的监视器上和在一台 400 nit 的手机上，1.0 对应的绝对亮度不同，但"看起来一样白"——因为观看环境和人眼适应也跟着变了。

这带来一个常见误会："SDR 就是 100 nits"。不是。SDR 文件只规定"1.0 是这台显示器的白"，具体多少由显示器和校准决定；100 是创作/校准环境的参考值，手机在户外可以轻松把 SDR 白推到 500 nits 以上。真正固定的是**相对关系**，不是绝对数字。

### 2.1 sRGB 和 BT.709 不是一回事

两者原色和白点相同，但：

* **传递函数不同**：sRGB 是分段函数（暗部线性段 + 约 2.4 的幂段），BT.709 的 OETF 是 `1.099·L^0.45 − 0.099` 一类形式。数值上接近，但不能互相套公式。
* **用途不同**：sRGB 面向显示器和网络图片，BT.709 面向电视制作与传输，还有有限/全范围、色度采样等视频侧约定。
* **参考白不同**：sRGB 本身不规定绝对亮度；BT.1886 规定 100 cd/m²。

所以一张"符合 sRGB"的 PNG 和一段"符合 BT.709"的视频，即使原色一样，码值也不能直接对拷。本项目输入按 sRGB 处理（ICC 转 sRGB、线性化用 sRGB 分段公式），输出再转到 BT.2020。

## 3. HDR 的两套约定

HDR 没有"一个"标准，而是两条路线，区别在于**参考的是场景还是显示**。

### 3.1 PQ：绝对显示参考

SMPTE ST 2084（2014）定义了 PQ（Perceptual Quantizer）[\[5\]](#r5)，后来被 ITU-R BT.2100 收为 HDR 的推荐传递函数之一[\[4\]](#r4)。它的核心是把**绝对亮度**映射到 0–1 的信号：

* 信号 0 → 0 cd/m²
* 信号 1 → 10000 cd/m²
* 中间按人眼对比敏感度分配码值，接近"感知均匀"

因为是绝对映射，同一个 PQ 码值在任何合规显示器上都应显示同一个亮度（在显示器能力范围内）。这让 HDR 可以"按母版意图"还原，但也带来兼容问题：把 PQ 信号直接丢给 SDR 显示器，它会把 0.58 当成"中灰"，而 0.58 其实是 203 nits——于是画面发灰、发平。这就是"PQ 直传 SDR 会发灰"的原因（见 [02](02-pq-and-brightness.md) 第 8 节）。

### 3.2 HLG：相对场景参考

HLG（Hybrid Log-Gamma）由 BBC 和 NHK 提出，同样收进 BT.2100[\[4\]](#r4)。它参考的是**场景光**，不是显示光：

* 低段是传统 gamma 曲线，所以老式 SDR 显示器"直接显示"也能看个大概（向后兼容）；
* 高段是对数曲线，压缩高光；
* 显示端再施加一个 **OOTF**（光光转换函数），系统 gamma 约 1.2，把场景线性映到显示亮度，峰值由显示器决定。

HLG 的"相对"意味着：同一个 HLG 文件在 1000 nit 和 600 nit 的显示器上都"合理"，只是峰值不同；代价是绝对亮度不确定，调色时要用参考显示器和 75% 信号约定来对齐。

### 3.3 203 cd/m²：HDR 的"参考白"

BT.2408（HDR 电视制作操作指南）把 **HDR Reference White 定义为 203 cd/m²**：由 HDR 摄像机拍摄 100% 反射率白卡得到的标称信号电平[\[6\]](#r6)。EBU 的 HLG 显示适配计算器写得更直接：**HLG 信号 75% 在 1000 cd/m² 峰值、参考观看环境下产生 203 cd/m²**[\[7\]](#r7)。

这个 203 不是随便定的，可以从 HLG 推出来：

```text
HLG 信号 75%  →  逆 OETF  →  场景线性 E ≈ 0.265
显示亮度 = 峰值 × E^1.2 = 1000 × 0.265^1.2 ≈ 202.5 cd/m²
```

（OOTF 的 gamma 取 1.2；不同文档会写 1.2 或按环境微调，结果在 200–204 之间。）

于是有三条常用等价说法，指的是同一个点：

| 说法                               | 数值            |
| -------------------------------- | ------------- |
| 100% 反射白卡在 1000-nit HLG 参考显示上的亮度 | 203 cd/m²     |
| 该亮度在 HLG 信号里的位置                  | 75%           |
| 该亮度在 PQ 信号里的位置                   | 约 58%（0.5807） |

最后一行常被忽略：**同一个 203 nits，在 PQ 里是 58% 信号，不是 75%**。把 HLG 的 75% 当成 PQ 的 75%，会把参考白错放到约 1000 nits，画面整体过曝。这个坑在第 [02](02-pq-and-brightness.md) 篇会展开。

> 注意：203 是**制作约定**，不是物理常数。BT.2408 自己也在更新（当前可见版本为 BT.2408-9，2026-03）；不同节目、不同平台可能用 100–250 nits 之间的参考白。本项目取 203，是为了和 Android Ultra HDR / BT.2408 生态对齐。

## 4. 标准族谱：谁管什么

HDR 涉及的标准经常被并列引用，其实分工很清楚。

| 标准                              | 类型   | 管什么                           | 不管什么       |
| ------------------------------- | ---- | ----------------------------- | ---------- |
| ITU-R BT.709[\[2\]](#r2)        | 建议书  | HDTV 的原色、OETF、参数              | HDR、显示绝对亮度 |
| ITU-R BT.1886[\[1\]](#r1)       | 建议书  | SDR 显示器的参考 EOTF（100 cd/m²）    | 内容制作、HDR   |
| ITU-R BT.2020[\[3\]](#r3)       | 建议书  | UHDTV 的原色（更宽）、两种传递函数、参数       | 具体显示亮度、元数据 |
| ITU-R BT.2100[\[4\]](#r4)       | 建议书  | HDR 电视：PQ 与 HLG 两套系统、参考环境     | 文件封装、增益图   |
| SMPTE ST 2084[\[5\]](#r5)       | 标准   | PQ 的精确数学定义                    | 怎么用、怎么封装   |
| ITU-R BT.2408[\[6\]](#r6)       | 报告   | HDR 制作操作实践：203 nits、信号电平、上下变换 | 强制合规       |
| SMPTE ST 2086                   | 标准   | 母版显示元数据（最大/最小亮度、原色）           | 消费端怎么处理    |
| CTA-861.3                       | 行业标准 | HDR10 的静态元数据（MaxCLL/MaxFALL）  | 动态元数据      |
| ISO/IEC 21496-1[\[10\]](#r10)   | 国际标准 | 增益图元数据（JPEG/HEIF/AVIF 通用）     | 增益图怎么算     |
| Android Ultra HDR[\[11\]](#r11) | 厂商规范 | JPEG 里装增益图的具体布局（MPF+XMP+ISO）  | 其它容器       |

几个常见"格式名"其实不是标准文件，而是**标准组合 + 生态约定**：

* **HDR10**：BT.2020 原色 + PQ + 10bit + SMPTE ST 2086 静态元数据（可选 MaxCLL/MaxFALL）。开放、免费，蓝光和流媒体最常用[\[13\]](#r13)。
* **HDR10+**：在 HDR10 基础上加**逐帧/逐场景动态元数据**，开放授权。
* **Dolby Vision**：专有，母版常为 12bit，动态元数据，编码常用 ICtCp；需要授权和设备支持[\[12\]](#r12)。
* **HLG**：BT.2100 的另一条路线，广播和直播友好，向后兼容 SDR。
* **Ultra HDR / 增益图**：静态图片的"兼容式 HDR"，SDR 基图 + 增益图 + 元数据，老设备看基图，新设备还原 HDR。

## 5. HDR 到底"多"了什么

不是"整张图更亮"。一张调色正确的 HDR 图，漫反射白仍然在 203 nits 左右，和 SDR 的 100–200 nits 相差不大；真正的差别在三个地方：

1. **高光余量**：镜面反射、灯泡、太阳、水面反光可以到 1000–4000 nits，而 SDR 在 100 nits 就削顶了。HDR 让这些区域有层次，而不是一片死白。
2. **暗部层次**：黑位更低（OLED 接近 0），同时 PQ 在暗部给了更多码值，暗部渐变不容易断层。代价是暗部对位深和噪声更敏感。
3. **色域**：BT.2020 覆盖约 75.8% 的 CIE 1931 色度面积，BT.709 只有约 35.9%[\[9\]](#r9)。更饱和的红、绿、青可以表示出来。

这三件事里，**增益图主要解决第 1 件**，顺带影响第 2 件（暗部乘数接近 1，基本不动），第 3 件靠输出容器的 BT.2020 标记，不是靠算法"造"出来的颜色。

### 5.1 为什么不能靠"整体提亮"

把 SDR 图整体乘 2，白墙、天空、皮肤会一起过曝，暗部噪点也会被放大。HDR 的正确做法是**只抬那些"本来就该更亮"的区域**，其余保持。这就是 tone mapping 和 inverse tone mapping（ITM）要解决的问题：

* **全局 tone mapping**：一条曲线压所有像素，简单但会压平局部对比。
* **局部 tone mapping**：按邻域自适应，能保住局部对比，但容易出光晕、梯度反转。
* **感知自适应**（Chapiro 2023 等）：按人眼在不同亮度下的适应状态分配，目标不是"数学正确"而是"看起来对"[\[14\]](#r14)。

ITM 则是反向：从已经削顶的 SDR 猜 HDR。猜错了就是"高光膨胀""暗部过提""材质变塑料"。照片上的 ITM 模型（通常假设自然图像的亮度分布）搬到二次元插画上经常翻车，因为插画的亮度分布是**画师画出来的**，不是物理成像的结果。

本项目的选择是第三条路：**不猜像素，只存比值**。基图原封不动，另存一张"每个像素还能亮多少倍"的增益图，显示端按自己的能力乘上去。这样 SDR 设备看到的还是原图，HDR 设备看到的是"原图 × 增益"，不存在"猜错纹理"的问题——只存在"增益估得对不对"的问题（见 [04](04-gain-map.md)）。

## 6. 本项目在标准地图上的位置

输入：8bit SDR 图片，按 sRGB 解释（ICC 转换、EXIF 转正、alpha 合成）。

处理：sRGB 码值 → 线性光 → 先建一张光场图（光源、传播、辐照度、AO、深度）→ 用启发式估计每个像素的"发光度" → 得到逐通道增益 `g_c ∈ [1, 2^gmax_c]` → HDR 线性光 = SDR 线性光 × g\_c。

输出六种容器：

| 容器              | 动态范围表达                                   | 参考白约定               |
| --------------- | ---------------------------------------- | ------------------- |
| JPEG（Ultra HDR） | 基图 8bit SDR + 8bit RGB 增益图 + XMP/ISO 元数据 | SDR 基图；增益乘到 HDR 白   |
| PNG 16bit       | PQ，BT.2020                               | 绝对，SDR 白 = 203 nits |
| HEIC 10/12bit   | PQ，BT.2020                               | 同上                  |
| AVIF 12bit      | PQ，BT.2020                               | 同上                  |
| JXL 24bit       | PQ，BT.2020                               | 同上                  |

六种产物统一 PQ；HLG 作为标准仍有效，但本工具不再输出（理由见 [02](02-pq-and-brightness.md) 第 7.1 节）。

数值链的关键一步是：**把 SDR 线性 1.0 定义为 203 nits**。于是

```text
HDR 绝对亮度 (nits) = sRGB 线性值 × 增益_通道 × 203
整图峰值 (nits)      = max(sRGB 线性值 × 增益_通道) × 203
```

`gmax` 上限 1.45，所以亮度意义上的标称峰值约 `203 × 2^1.45 ≈ 555 nits`；单通道权重与色偏最多再高 20–30%，饱和色高光可以摸到 700 nits 量级，但会被 `finalize` 的软拐点压住，不会真的打满。实际峰值取决于画面里最亮的 SDR 像素：样图实测 486 nits（三通道 gmax 1.20/1.21/1.37），刚好落在"手机 HDR 屏能明显看出差别、又不会把白墙推爆"的窗口里。

## 7. 常见误解

1. **"HDR 就是更亮。"** 不是。HDR 是更大的**余量**；参考白仍是 203 左右，乱提整体亮度只会过曝。
2. **"8bit 不能存 HDR。"** 能存 PQ 码值，但暗部只有几十个台阶，渐变会 banding。所以 HDR 分发普遍要求 10bit 起，母版 12bit。
3. **"增益图会改变 SDR 显示。"** 不会。基图是独立的、完整的 SDR 图像；增益图只在支持它的查看器里被读取。
4. **"HDR 文件在 SDR 屏上一定难看。"** 取决于查看器。PQ 直传且不做映射会发灰；带增益图的文件在 SDR 屏上退化成基图，反而正常。
5. **"峰值越高越好。"** 受 ABL（自动亮度限制）、观看环境、内容意图共同约束。把 203 的白推到 1000 只会让人眼不适。
6. **"sRGB 和 BT.709 可以互换。"** 原色相同，传递函数和范围约定不同，码值不能直接对拷。
